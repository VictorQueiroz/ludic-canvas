Virtual collections
The collection suite compares 400 and 4,000 retained rows with matching virtualized lists, then probes a 40,000-item virtualized list. Contents, fonts, viewport, row sizes, padding and scroll trace match within each pair. The 40,000-item probe has no retained comparator. Commands are applied before the measured frame, so synchronous window commits are included. The trace advances 12 CSS pixels per frame and jumps to distant regions every 30 requested frames. Mounted node counts and actual offsets are retained. Initial item indexing and application data remain linear in item count.
Run several times, alternate the workload order, and compare matching configurations. Enable stage profiles to investigate layout, scroll/window commits, paint/submission and accessibility work; use a separate unprofiled run for your timing budget. The collection guide explains selection, focus and the fixed-height contract.
Original HUD baseline
Each workload warms up for 20 frames, then records the requested sample count. Static HUD and responsive layout use 96 cards, telemetry uses 48 cards updated every six frames, and inventory scroll uses 400 retained rows with deterministic focus targets. Two root-local atlas registrations exercise an ASCII primary face and Latin-1 fallback. The responsive workload alternates a 360/960 CSS-pixel width, constrained by the available container. Five scene creation/teardown cycles follow.


CPU frame time is elapsed time around ui.frame(), including layout, painting, accessibility synchronization and WebGL submission. Frame intervals are requestAnimationFrame timestamp differences. Render-to-commit records scheduling latency through a React layout effect. These are distinct measurements; none measures GPU execution or confirms presentation. Raw samples use milliseconds and summaries use nearest-rank percentiles.


The initial setup duration uses the browser's existing cache state. No cold-cache claim is made. The harness does not measure heap or GPU memory; removing every accessibility mirror is only a teardown check. A hidden tab or lost context stops the run. Set budgets for your device and workload before running; absent budgets are reported as not-set.


Reports identify repository source, which can differ from the npm release with the same package version. A revision ending in -dirty means local changes were present at build time. CI uses short software-rendered smoke runs to check the report contract and cleanup; timing thresholds are left unset.


Recorded desktop baseline
A Chrome 156 / Apple M3 run acquired 120 samples per workload and five teardown cycles. CPU frame-call p95 was 9.5 ms for the static HUD and 26.9 ms for the 400-row inventory. These UI-only results motivate profiling large collections; they do not establish the cause of the difference. Budgets were unset. Read the environment, source revision and qualification status, or download the original JSON and checksum before comparing results.


Measured collection comparison
Three isolated Chrome 156 / Apple M3 runs measured 4,000 retained rows at 49.4–54.5 ms CPU frame-call p95, compared with 2.7–3.5 ms for the matching virtualized list. The 400/4,000/40,000-item virtualized cases all met the supplied 4 ms p95 budget on that machine; a separate diagnostic recorded 51–63 mounted nodes. These are UI-only, repository-source results with uncontrolled background applications and caches.
